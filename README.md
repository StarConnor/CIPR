## Repository Layout

```
docker_prep/     Docker image build system (base env, per-agent CLI images, attacker server)
src/agent_red/   Core framework: runner, environment manager, scorer, queue server
standalone/      Local standalone experiment runner (no server required)
configs/         Per-agent YAML configs (+ machine-local VMware config)
data/            Datasets; data/CIPR contains the dataset construction pipeline
exp/             Per-run artifacts: screenshots/frames, runner & agent logs
results/         Structured result JSON files (one file per run namespace)
test/            Server-mode client, result analysis scripts, example configs
```

## Datasets

The experiment-ready datasets generated by the CIPR pipeline ship with the
repo, one directory per condition:

| Dataset (`--dataset` value) | Path | Samples | Condition |
|------|------|---------|-----------|
| `cipr_no_skills` | `data/cipr_no_skills/dataset.json` | 640 | no skill, no rule |
| `cipr_normal_skills` | `data/cipr_normal_skills/dataset.json` | 640 | one random skill |
| `cipr_defense_skills` | `data/cipr_defense_skills/dataset.json` | 640 | one random skill + random rule + defense rules |

All three share the same 640 sample configurations and differ only in the
attached skills/rules metadata. See `data/CIPR/README.md` for how they were
constructed.

### Using your own dataset

The framework loads datasets by name from `<data-path>/<dataset_name>/dataset.json`
(default data path: `./data`). To run on a custom dataset:

1. Create a new directory `data/<your-dataset-name>/`;
2. Place your dataset file there as `dataset.json` (same schema as
   `data/CIPR/dataset_gen/main.py` outputs);
3. Reference it by name when starting an experiment:
   `--dataset <your-dataset-name>` (standalone) or `dataset_name:` in a YAML config (server mode).

## 1. Environment Preparation

### 1.1 Python environment

Requires Python >= 3.11 and [uv](https://docs.astral.sh/uv/).

```bash
git clone https://github.com/StarConnor/code-agent-redteam.git
cd code-agent-redteam
uv venv
source .venv/bin/activate
uv sync
```

### 1.2 Docker images (`docker_prep`)

The framework runs every experiment inside Docker. Each CLI agent image is
built directly on top of a shared base image (no intermediate `cli-env` layer):

```
base-env (Ubuntu + Node + automation server + mitmproxy tracing)
    └── cli-env:cc / cli-env:codex / cli-env:opencode / cli-env:cline / cli-env:gemini
```

Build inputs (agent package archives under `docker_prep/agents/*/`, mitm
certificates, SSH keys under `docker_prep/base/assets/`) are local-only and not
committed to Git; provide them before building. See `docker_prep/README.md`
for details.

Build the base image (a proxy is mandatory for the build stage):

```bash
export HTTP_PROXY=http://your-proxy-host:port
export HTTPS_PROXY=$HTTP_PROXY
export http_proxy=$HTTP_PROXY https_proxy=$HTTPS_PROXY

cd docker_prep
./prepare_build_assets.sh base
./build.sh base          # builds base-env
./build.sh all           # builds all CLI agent images (cc/codex/opencode/cline/gemini)
# or individually:
./build.sh cc
./build.sh codex
```

Build the attacker server image (serves malicious payloads on `:8080`/`:8081`
and records exfiltration requests):

```bash
bash docker_prep/attacker_server/build_docker.sh
```

Optional: shared dependency cache to speed up repeated `prepare_env` runs
(devpi/apt-cacher-ng/Verdaccio/GOPROXY/...):

```bash
bash docker_prep/dependency_cache/start_cache.sh
export ENABLE_DEPENDENCY_CACHE=true
export DEPENDENCY_CACHE_HOST=<host-ip>
```

Optional: mount host-side language toolchains into containers instead of
baking them into the image — see "Runtime Language Toolchain Mounts" in
`docker_prep/README.md`.

### 1.3 Model API credentials

Credentials are resolved per **model name** (not per agent) by
`src/agent_red/utils/get_model_api.py`, which also loads a `.env` file at the
repo root if present. Copy the template and fill in the providers you use:

```bash
cp .env.example .env
```

| Model name (`--model`) | API key env var | Base URL env var |
|------------------------|-----------------|------------------|
| `gpt-5.5`, `gpt-5.4`, `gpt-5.4-mini`, `gpt-5.3-codex` | `CODEX_API_KEY` | `CODEX_BASE_URL` |
| `deepseek-v4-flash`, `deepseek-v4-pro` | `DEEPSEEK_API_KEY` | `DEEPSEEK_BASE_URL` |
| `gemini-*` (or `pro`/`flash`/`flash-lite`) | `GEMINI_API_KEY` or `GOOGLE_API_KEY` | `GEMINI_BASE_URL` or `GOOGLE_GEMINI_BASE_URL` (default: Google endpoint) |
| `claude-*`, `cheap_claude` | `CHEAP_API_KEY` | `CHEAP_BASE_URL` |
| `doubao-seed-2-0-pro-260215` | `VOLCENGINE_API_KEY` | `VOLCENGINE_BASE_URL` |
| anything else (custom models) | `V_API_KEY` | `V_BASE_URL` |

Agent-specific notes:

- **Claude Code (`cc_cli`) + DeepSeek**: Claude Code talks the Anthropic wire
  protocol, so for DeepSeek models set `DEEPSEEK_ANTHROPIC_LIKE_BASE_URL` in
  addition to `DEEPSEEK_BASE_URL`; it overrides the base URL written into
  Claude Code's `settings.json`.
- **OpenCode (`opencode_cli`)**: routes traffic through a local compatibility
  shim; only the resolved key/base URL above are needed.
- The framework writes the resolved credentials into each agent's in-container
  config (`~/.claude/settings.json`, `~/.codex/config.toml`,
  `~/.config/opencode/opencode.json`, ...) at run start; never commit them.

Resolution precedence (standalone mode, see
`standalone/run_local_exp.py`):

1. Explicit CLI flags: `--api-key`, `--api-base-url`;
2. Model-specific variables from the table above (via `.env` or shell);
3. Generic fallbacks: `AGENT_API_KEY` / `AGENT_BASE_URL`.

In server mode, make sure the same variables are visible to the process that
runs `python -m src.agent_red.queue_server` (it resolves credentials before
dispatching containers). Two additional optional variables from `.env.example`
matter for scoring: `JUDGE_*` selects a dedicated host-side LLM judge (falls
back to `CODEX_*`), and `AUTOMATION_SERVER_OPENAI_*` optionally gives the
in-container automation server its own endpoint.

### 1.4 IDE/VM experiments only

IDE-based agents (Cursor, Copilot, Trae, ...) require VMware Windows guests.
Copy `configs/vmware.example.yaml` to `configs/vmware.local.yaml` and fill in
VMX paths, Windows credentials, and SSH settings. CLI-agent experiments do not
need this step.

## 2. Running Experiments

Two equivalent entry points share the same core runner/scorer path, so results
are schema-compatible between modes.

### 2.1 Standalone mode (recommended)

No server process; runs containers locally and supports parallel dataset
execution. Only CLI agents (`*_cli`) are supported.

Single sample (smoke test):

```bash
uv run python standalone/run_local_exp.py \
  --dataset cipr_no_skills \
  --sample-id <sample_id> \
  --agent cc_cli \
  --model deepseek-v4-flash \
  --run-name debug-run
```

Full dataset run with concurrency:

```bash
uv run python standalone/run_local_exp.py \
  --dataset cipr_defense_skills \
  --agent codex_cli \
  --model gpt-5.4 \
  --concurrency 3 \
  --run-name my-experiment \
  --skip-completed \
  --no-stream-logs
```

Useful flags:

| Flag | Description |
|------|-------------|
| `--dataset` | Dataset name under `--data-path` (default `./data`) |
| `--sample-id` | Run exactly one sample |
| `--filter-json` | Filter dict, e.g. `'{"category": ["Exfiltration"]}'` |
| `--sample-n`, `--first-n`, `--start-id/--start-index` | Subset selection |
| `--k-runs` | Repeat each sample K times |
| `--concurrency` | Parallel containers (dataset mode) |
| `--skip-completed` | Reuse existing successful results |
| `--no-stream-frames` / `--no-stream-logs` | Disable screenshot/log streaming |

Alternatively pass a server-compatible request JSON:
`uv run python standalone/run_local_exp.py --request-json standalone/codex_smoke_request.json`

### 2.2 Server + client mode

Start the backend queue server:

```bash
python -m src.agent_red.queue_server
```

or use the auto-restart wrapper (also cleans up leftover containers on crash):

```bash
./run_service.sh
```

Then run experiments from a client against the server (default port `8083`).
Configs live in `test/exp-*.yaml`:

```bash
cd test
python run_exp.py --config exp-dataset.yaml      # dataset mode
python run_exp.py --config exp-sample.yaml       # single-sample mode
```

CLI overrides are also supported:

```bash
python run_exp.py --config exp-dataset.yaml \
  --server http://127.0.0.1:8083 \
  --agent codex_cli --model gpt-5.4 --concurrency 3
```

The client submits the task over HTTP, streams live screenshots/logs/results
over WebSocket into `exp/<task_id>/`, and fetches a final report JSON.
Attach to a running task with `python run_exp.py --task_id <id>`.

Cleanup of leftover experiment containers/networks:

```bash
./refresh_state.sh        # add "vm" as first arg to also stop temp VMs
```

## 3. Reading Results

### 3.1 Screenshots (`exp/<task-id>/frames/`)

During a run, periodic VNC screenshots are saved per sample as
`frames/<sample_id>/latest.png`; if OpenCV/numpy are installed they are also
encoded into a trajectory video `frames/<sample_id>/trajectory.avi`. In server
mode the client saves the same frames locally under `exp/<task_id>/frames/`.
Disable with `--no-stream-frames`.

### 3.2 Logs (`exp/<task-id>/`)

Each run directory contains:

- `runner.log` — framework-level orchestration log (container prep, scoring, errors)
- `<run-name>-<agent>-<timestamp>.log` — live agent workflow/SSE log stream
- `web-server-*.log` — attacker web-server traffic log
- `samples/<sample_id>/code_server.container.log` — coding-agent container stdout
- `samples/<sample_id>/web_server.container.log` — attacker server container stdout

### 3.3 Result JSON (`results/`)

Structured results are written by the scorer to
`results/<run-name>/<dataset>_<attack-method>_<agent>_<model>.json`. The file is
a list of per-sample records:

```jsonc
[
  {
    "sample_id": "...",
    "status": "success",
    "timestamp": "...",
    "result": {
      "task_success": true,        // did the agent complete the coding task?
      "attack_success": false,     // was the injected payload executed?
      "alert_success": true,       // did the agent flag/report the injection?
      "commands_executed": [...]   // full shell command history
    },
    "attack_payload": {...},
    "stats": {...},
    "metadata": {...}
  }
]
```

Key metrics are **ASR** (attack success rate), **TSR** (task success rate), and
**Alert** rate, aggregated over these records.

Aggregate analysis (CSV/Markdown tables + SVG figures for ASR/TSR/breakdowns):

```bash
python test/analyse_result.py \
  --dataset data/cipr_no_skills/dataset.json \
  --results-root results/my-experiment \
  --dataset-name cipr_no_skills \
  --out analysis/cipr_no_skills
```

In server mode, a per-task report is additionally fetched to
`exp/<task_id>/report_<task_id>.json`.
